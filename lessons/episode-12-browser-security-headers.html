Security for Legal SaaS — Episode 12: Browser Security Headers

The Browser as Battleground

Your legal SaaS application runs in your users' browsers. Those browsers will happily execute JavaScript from any origin, embed your pages in iframes, and send credentials to any domain — unless you explicitly tell them not to. Browser security headers are instructions from your server to the browser, declaring what is and isn't permitted. Get them wrong, and you've handed attackers a proxy inside your user's authenticated session.

Key stat: The 2023 Verizon DBIR found that web application attacks constituted 26% of all breaches, with credential theft and session hijacking as primary objectives. Properly configured security headers eliminate entire classes of these attacks.

For legal tech — where a single authenticated session may access privileged case files, billing data, and client communications — browser-level protections are not optional polish. They are the last line of defence when everything else fails.

CORS: Who Gets to Read Your Responses

Cross-Origin Resource Sharing (CORS) controls which external origins can make requests to your API and read the responses. The Same-Origin Policy blocks cross-origin reads by default — CORS relaxes it selectively.

The Misconfiguration That Opens Everything

Configuration Risk Level Effect
Access-Control-Allow-Origin: *Critical (with credentials)Any website can read your API responses
Reflecting the Origin header backCriticalAttacker's domain gets access automatically
Access-Control-Allow-Credentials: true + wildcardCriticalExplicitly forbidden by spec but some servers try
Specific trusted origins onlyCorrectOnly your own domains can read responses

Real-world example: PortSwigger research demonstrated that CORS misconfigurations in production applications allowed attackers to steal user data cross-origin by simply reflecting the attacker's Origin header in the Access-Control-Allow-Origin response.

For legal SaaS: If your document API reflects any Origin header and includes Access-Control-Allow-Credentials: true, an attacker's website can silently read your user's privileged case documents while they have an active session.

Correct Implementation

Maintain a strict allowlist of permitted origins. Validate the incoming Origin header against this list. Only echo back origins that match exactly. Never use regex patterns that can be bypassed (e.g., *.lawfirm.com matching evil-lawfirm.com).

CSRF: Forged Actions in Your User's Name

Cross-Site Request Forgery tricks a user's browser into making state-changing requests to your application using their existing session cookies. The browser automatically attaches cookies to same-site requests — the attacker doesn't need to steal credentials.

Attack Scenario in Legal Tech

A lawyer visits a malicious page (perhaps linked in an email from opposing counsel). The page contains a hidden form that submits to your application's API:

  • POST /api/matters/{id}/share — shares a privileged case with an external email
  • POST /api/documents/{id}/access — grants document access to a new user
  • POST /api/billing/transfer — initiates a trust account transfer

Defence Layers

Defence How It Works
CSRF tokensServer generates a random token per session; form submissions must include it. Attacker's page cannot read it (Same-Origin Policy).
SameSite cookiesSameSite=Lax (default in modern browsers) blocks cookies on cross-site POST requests. Strict blocks them on all cross-site requests.
Origin/Referer validationVerify the Origin or Referer header on state-changing requests matches your domain.
Custom request headersRequire a custom header (e.g., X-Requested-With) that simple cross-origin forms cannot set.

The SameSite cookie attribute has dramatically improved the baseline — Chrome, Firefox, and Edge all default to Lax. But explicit CSRF tokens remain necessary for older browser support and defence-in-depth.

Content Security Policy (CSP)

CSP tells the browser exactly which sources of content are permitted — scripts, styles, images, fonts, frames, and more. A strict CSP is the most effective defence against Cross-Site Scripting (XSS).

CSP for Legal SaaS

Directive Purpose
script-src 'self' 'nonce-{random}'Only execute scripts from your domain or with a per-request nonce
frame-ancestors 'none'Prevent your app from being embedded in iframes (replaces X-Frame-Options)
form-action 'self'Forms can only submit to your own origin
base-uri 'self'Prevents <base> tag injection that redirects relative URLs

Deployment tip: Start with Content-Security-Policy-Report-Only to collect violation reports without breaking functionality. Report URI or your own endpoint receives JSON reports of what would have been blocked. Tighten over weeks, then enforce.

X-Frame-Options and Clickjacking

X-Frame-Options prevents your application from being embedded in an iframe on an attacker's page. Without it, an attacker overlays transparent iframes of your app over a decoy page — the user thinks they're clicking a harmless button but actually clicking "Share Document" or "Approve Transfer" in your application.

For legal SaaS: X-Frame-Options: DENY (or use the equivalent frame-ancestors 'none' in CSP). There is almost never a legitimate reason to allow external framing of a legal application.

HSTS: Forcing HTTPS

HTTP Strict Transport Security (HSTS) tells browsers to only connect to your domain over HTTPS — never HTTP. This prevents SSL stripping attacks where a man-in-the-middle downgrades the connection.

Submitting to the HSTS preload list hardcodes your domain into browser source code — HTTPS is enforced even on the first visit, before any header is received.

Headers as Defence-in-Depth

No single header stops all attacks. The security model is layered:

Attack Primary Defence Header Backup
XSSInput sanitisation + output encodingCSP blocks inline script execution
ClickjackingFrame-busting JSX-Frame-Options / CSP frame-ancestors
MITM downgradeTLS configurationHSTS forces HTTPS
Session hijackingSecure cookie flagsSameSite + CSP prevents exfiltration vectors
Data theft via embeddingAuthenticationCORS blocks cross-origin reads

Automated Scanning

Don't rely on manual header checks. Mozilla Observatory grades your site's security headers and provides specific remediation guidance. SecurityHeaders.com by Scott Helme offers instant analysis with explanations for each missing or misconfigured header.

Run these scans in CI/CD — a deployment that removes a security header should fail the pipeline, not reach production.

Conclusion

Browser security headers are cheap to implement and expensive to forget. A single misconfigured CORS policy can expose every privileged document your users access. A missing CSP allows injected scripts to exfiltrate session tokens. For legal SaaS, where the browser session is the gateway to attorney-client privilege, these headers are not optimisation — they are infrastructure.

Security headers are your instructions to the browser — here’s what’s permitted, everything else is blocked.

Dan: Let’s start with CORS. I see developers wrestling with this constantly — usually by setting Access-Control-Allow-Origin to star and calling it done.

Alice: Which is exactly the wrong answer. CORS — Cross-Origin Resource Sharing — controls which external websites can make requests to your API and read the responses. The browser’s Same-Origin Policy blocks cross-origin reads by default. CORS selectively relaxes that. When you set Allow-Origin to star, you’re saying any website on the internet can read responses from your API.

Dan: And for legal SaaS specifically?

Alice: If your document API reflects any Origin header back in Access-Control-Allow-Origin and includes Allow-Credentials: true, an attacker’s website can silently read your user’s privileged case files while they have an active session open in another tab. The lawyer visits a malicious link — maybe something that looked like a court notice — and in the background, JavaScript on that page is pulling their client’s merger documents through your API using their existing session cookie.

Dan: The fix being — only allow origins you explicitly trust?

Alice: Maintain a strict allowlist. Validate the incoming Origin header against that list. Only echo back exact matches. And never use regex patterns that can be tricked — something like “anything ending in lawfirm.com” will match “evil-lawfirm.com” too.

Dan: OK, next — CSRF. Cross-Site Request Forgery. How is that different from CORS issues?

Alice: CORS is about reading responses. CSRF is about triggering actions. The attack: a user visits a malicious page while logged into your application. That page contains a hidden form that submits to your API — maybe POST to /api/matters/share with an attacker-controlled email. The browser automatically attaches the user’s session cookie because it’s a same-site request from the browser’s perspective. Your server sees a valid authenticated request and executes it.

Dan: So the attacker never steals credentials — they just use the user’s existing session.

Alice: Exactly. For legal tech, the actions available through CSRF are devastating. Share a privileged case file with an external party. Grant document access. Approve a trust account transfer. Change notification settings so alerts go to an attacker-controlled email. All performed with the lawyer’s own authenticated session.

Dan: Defences?

Alice: Three layers. First — SameSite cookies. Set your session cookie to SameSite=Lax at minimum, which blocks cookies on cross-site POST requests. Modern browsers default to Lax, but be explicit. Second — CSRF tokens. Generate a random token per session, include it in every form and AJAX request, validate server-side. The attacker’s page can’t read this token because of the Same-Origin Policy. Third — validate the Origin or Referer header on all state-changing requests.

Dan: CSP next. Content Security Policy. I know this one has a reputation for being hard to deploy.

Alice: It is the single most effective defence against XSS — cross-site scripting. CSP tells the browser exactly which sources of content are allowed. If an attacker injects a script tag through an XSS vulnerability, but your CSP says “only execute scripts from my own domain with a specific nonce” — the injected script simply doesn’t run. The browser blocks it.

Dan: What does a good CSP look like for a legal SaaS app?

Alice: Start with default-src self — nothing loads from external sources unless explicitly permitted. Script-src self with a per-request nonce — no inline scripts without the nonce, no eval. Frame-ancestors none — your app can’t be embedded in iframes. Form-action self — forms can only submit to your own origin. This blocks both XSS payload execution and clickjacking in one header.

Dan: You mentioned it’s hard to deploy. Why?

Alice: Because most applications have inline scripts, third-party analytics, CDN-loaded libraries, and embedded widgets that a strict CSP will break. The solution — start with Content-Security-Policy-Report-Only. Same syntax, but violations get reported instead of blocked. Collect reports for a few weeks, identify legitimate sources, add them to your allowlist, then switch to enforcement mode. Iterate, don’t deploy blind.

Dan: What about X-Frame-Options and HSTS?

Alice: X-Frame-Options: DENY prevents your app from being embedded in iframes. Without it, an attacker overlays a transparent iframe of your application over a decoy page. The user thinks they’re clicking “Download Cat Photo” but they’re actually clicking “Share Case File” in your invisible iframe. For legal SaaS — there’s almost never a legitimate reason to allow external framing.

Dan: And HSTS?

Alice: HTTP Strict Transport Security tells the browser to only connect over HTTPS — never HTTP. Without it, a man-in-the-middle on the network can downgrade the connection and intercept everything. Set max-age to at least one year, include subdomains, and submit to the HSTS preload list so enforcement starts on the very first visit, before any header is received.

Dan: These headers feel like they should be set-and-forget. Are they?

Alice: They should be, but they drift. A developer adds a new third-party integration and weakens the CSP. Someone removes HSTS during debugging and forgets to restore it. A new subdomain launches without headers configured. The solution — scan in CI/CD — your Continuous Integration and Continuous Deployment pipeline, the automated system that builds, tests, and deploys your code. Mozilla Observatory and SecurityHeaders.com both provide automated grading. A deployment that removes a security header should fail the pipeline.

Dan: The mental model here is defence-in-depth?

Alice: Precisely. No single header stops all attacks. CSP catches XSS that input sanitisation missed. SameSite cookies catch CSRF that missing tokens would allow. HSTS catches TLS downgrades that certificate configuration alone can’t prevent. Each layer covers gaps in the others. For legal SaaS, where a single compromised session exposes attorney-client privilege, you want every layer active.
